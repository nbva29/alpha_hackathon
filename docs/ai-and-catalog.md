# Справочник продуктов и необязательный ИИ

## Зачем нужен справочник

Предприниматель описывает задачу обычными параметрами: цель, категория, сумма и срок. Ему нужны условия и причины, почему вариант подходит или нет. Источник условий в прототипе — таблица `credit_products` в PostgreSQL (`backend/app/models/entities.py`), первоначально заполняемая шестью синтетическими записями из `backend/app/services/catalog.py`. Тарифы не являются действующими предложениями банка.

В записи есть `id`, `version`, название, категория, назначение, минимальная и максимальная сумма и срок, ставка, требования к возрасту бизнеса и выручке, тип обязательного документа и дополнительные условия. Категории: развитие (`development`), оборотные средства (`turnover`), овердрафт (`overdraft`). Справочник читается через `GET /api/credit-products` и `GET /api/credit-products/{id}`; пользовательские данные туда не записываются.

`POST /api/credit-products/recommendations` сравнивает параметры потребности с каждым активным продуктом и возвращает `fits` и конкретные `reasons`: другая цель, сумма или срок вне диапазона, недостаточный срок работы бизнеса или выручка. Подходящие предложения сортируются первыми, затем по ставке. На экране сравнения показываются ставки, диапазоны, ориентир платежа и дополнительные условия. Это **правила каталога**, а не кредитное решение. При создании заявки сохраняется версия выбранного продукта и снимок компании. Редактора справочника нет; полный снимок условий продукта не сохраняется, поэтому ручное изменение записей БД после создания заявки может изменить дальнейшие проверки или показ условий. Для промышленного процесса нужна неизменяемая версия условий.

## Почему ИИ включён и где его границы

Для пользователя без банковской экспертизы естественный вопрос («какой документ нужен?», «почему запросили сведения?») проще формы поиска. Помощник превращает данные справочника и заявки в краткое объяснение. Ценность ИИ — навигация и понятный ответ, а не управление риском. Подбор, ограничения продукта, платежи, статусы и решение банка остаются детерминированными. Модель не получает инструменты изменения заявки и не может одобрить кредит.

Перед вызовом модели backend выбирает релевантные активные записи из той же таблицы `credit_products`, передаёт их с ID и версией, а в ответе API показывает `sources`. Для вопроса по заявке сначала проверяется её владелец; модель может получить контекст компании, параметров заявки, статусов, проверок и имён/типов документов. **Содержимое загруженных файлов не передаётся.** При сравнении двух выбранных продуктов backend умеет вернуть проверенное сравнение по данным каталога. Ответ с неизвестной ставкой или несуществующим продуктом отбрасывается в пользу справочного ответа без модели. Эти ограничения уменьшают риск ошибки, но не гарантируют фактическую точность любого свободного текста модели.

## Запуск без модели — обязательный базовый вариант

Из корня проекта выполните `docker compose up --build` и откройте `http://localhost:8080`. PostgreSQL, `bank-mock`, backend и frontend работают в Docker. Никакая ИИ-служба для создания, рассмотрения и завершения заявки не нужна. Если inference недоступен или `AI_BASE_URL` пуст, `/api/assistant` отвечает с `mode: deterministic-fallback`. Если две выбранные карточки сравниваются по проверенным данным, возможен `mode: verified-comparison`. Оба режима работают без модели.

## Локальная модель отдельно от Docker

1. Получите модель **с открытыми весами**. По умолчанию проект настроен на [Qwen3-4B-Instruct-2507](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507); допустимый пример другой модели — [Qwen2.5-7B-Instruct](https://huggingface.co/Qwen/Qwen2.5-7B-Instruct). Официальные карточки указывают лицензию Apache-2.0. Квантованная сборка и её лицензия должны соответствовать выбранным весам.
2. Запустите модель в LM Studio или другом сервере, который предоставляет OpenAI-совместимый `POST /v1/chat/completions`. Включите локальный сервер и узнайте **точное имя загруженной модели**, которое он принимает в поле `model`. Для LM Studio сервер обычно доступен на порту `1234`; при Docker backend он должен быть доступен контейнеру через `host.docker.internal`.
3. Для Docker Compose скопируйте корневой `.env.example` в `.env` и укажите `AI_BASE_URL=http://host.docker.internal:1234/v1`, `AI_MODEL=<точный ID модели>`. Для запуска backend без Docker используйте `backend/.env` и `AI_BASE_URL=http://127.0.0.1:1234/v1`. Перезапустите backend после изменения переменных.
4. Войдите как `anna@demo.local`, откройте помощника и спросите: «Какой документ нужен для овердрафта?». Ответ API `/api/assistant` должен содержать `mode: local-llm` и `sources` с карточками овердрафта. `deterministic-fallback` означает, что модель не ответила; это не подтверждение работы ИИ.

Альтернативный полностью контейнерный запуск Ollama описан в README. Модель загружается отдельно в необязательном Compose-профиле `ai`; её отсутствие не влияет на основной процесс.

## Модель или endpoint эксперта

Эксперт может указать собственный `AI_BASE_URL`, `AI_MODEL` и при необходимости `AI_API_KEY` в **корневом `.env` для Docker Compose**. Для backend вне Docker те же параметры задаются в `backend/.env`. Ключ передаётся как `Authorization: Bearer <AI_API_KEY>` и не должен попадать в Git. По умолчанию разрешены только локальные HTTP-адреса `localhost`, `127.0.0.1`, `host.docker.internal`, `ollama`. Для HTTPS-адреса через интернет нужно явно установить `AI_ALLOW_REMOTE=true`. Произвольный внешний HTTP не допускается. Адрес должен вести к OpenAI-совместимому API; backend добавляет `/chat/completions` к указанному base URL.

Пример корневого `.env` для необязательного внешнего сервера:

```dotenv
AI_BASE_URL=https://models.example.org/v1
AI_MODEL=exact-open-weight-model-id
AI_API_KEY=replace-with-own-key
AI_ALLOW_REMOTE=true
```

При таком подключении на сервер модели уходят вопрос и описанный выше контекст клиента. Используйте только сервер, которому разрешено передавать синтетические данные прототипа. Доступность внешнего endpoint, его бесплатность и открытость весов выбранной модели обеспечивает тот, кто предоставляет endpoint; отправляемый на проверку базовый сценарий от него не зависит. Историческое значение поля ответа `mode: local-llm` обозначает успешный вызов настроенной модели, в том числе внешней.

## Распознавание банковских выписок

Сейчас распознавания выписок **нет**: файл загружается и сохраняется, а `bank-mock` проверяет наличие документа нужного типа. Поэтому в состав передаваемой версии не входит модель OCR и не требуется отдельный запуск OCR-сервера. Если распознавание будет добавлено, оно должно оставаться необязательным для основного пути; в документации потребуется указать конкретную модель с открытыми весами, ссылку на веса и лицензию, команду запуска и проверочный пример с синтетической выпиской.
