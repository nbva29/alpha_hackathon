# Альфа-Хак 2026 — Smart Credit Cabinet

Демонстрационный проект кабинета предпринимателя. Все проверки, скоринг, решения и выдача кредита синтетические; реальные ФНС, БКИ и денежные переводы не используются.

## Состав системы

- `backend/` — FastAPI API, SQLAlchemy, PostgreSQL, cookie-сессии, документы, история статусов, аудит, необязательный LLM-помощник с поиском по каталогу и резервным ответом без модели.
- `bank-mock/` — отдельный внутренний сервис имитации проверок и скоринга. Он не доступен с хоста через порт; сотрудник работает через backend API.
- `docker-compose.yml` — PostgreSQL, backend, bank-mock и frontend.
- `frontend/` — React-клиент, подключённый к FastAPI через `/api`; сессия хранится в HttpOnly cookie, заявки и документы — на backend.

Клиентский сценарий и кабинет сотрудника работают с серверными данными. `frontend/src/mock-api.ts` остался только как набор типов, подписей статусов и старый тестовый симулятор; интерфейс не вызывает его операции хранения.

## Запуск

Требуется Docker Desktop / Docker Engine и Compose.

```bash
cp .env.example .env  # необязательно; параметры Compose, включая ИИ
# В корне проекта:
docker compose up --build
```

- Frontend: http://localhost:8080
- Backend OpenAPI: http://localhost:8000/docs
- Backend health: http://localhost:8000/health
- Bank mock health: `http://bank-mock:8001/health` внутри compose-сети

Остановить стек: `docker compose down` (добавьте `-v`, чтобы удалить демо-данные PostgreSQL и загруженные файлы).

### Локальный запуск без Docker

Нужны два процесса Python (backend и bank-mock) и один процесс frontend.

```bash
# Терминал 1: bank-mock
cd bank-mock
python -m venv .venv
# Windows: .venv\Scripts\activate ; macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --host 127.0.0.1 --port 8001

# Терминал 2: backend
cd backend
cp .env.example .env
python -m venv .venv
# Windows: .venv\Scripts\activate ; macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload

# Терминал 3: frontend
cd frontend
npm ci
npm run dev
```

- Frontend dev server: http://127.0.0.1:5173
- Backend OpenAPI: http://127.0.0.1:8000/docs
- Bank mock health: http://127.0.0.1:8001/health

Без `DATABASE_URL` используется SQLite `./alfa_demo.db`; в Compose — PostgreSQL с постоянным volume. Для production необходимо задать уникальные `SECRET_KEY` и `BANK_INTERNAL_KEY`, включить HTTPS и установить `COOKIE_SECURE=true`. Демо-пароли предназначены только для локального хакатона.

## Тестовые аккаунты

- `anna@demo.local` / `demo123` — устойчивый профиль компании и сценарий, который может пройти демо-скоринг.
- `maxim@demo.local` / `demo123` — тестовый профиль с коротким сроком работы и синтетической просрочкой.
- `bank@demo.local` / `demo123` — сотрудник банка, очередь заявок и деморешения.

Регистрация отсутствует. При первом старте создаются два предпринимателя, сотрудник, компании и каталог продуктов. У каждого предпринимателя собственные данные.

## Авторизация и безопасность

- Серверная сессия в случайной opaque-cookie `alfa_session`, `HttpOnly`, `SameSite=Lax`, срок по умолчанию 8 часов.
- В БД хранится SHA-256 хеш session-токена, время истечения и отзыв сессии; сам session-токен не сохраняется.
- Для изменяющих запросов обязателен `X-CSRF-Token`, выданный при login или через `/api/auth/me`; проверяется `Origin` при его наличии.
- Пароли хранятся как salted scrypt-хеши (memory-hard KDF). Нет регистрации и админ-панели. Роль сотрудника проверяется сервером отдельно от роли предпринимателя.
- Все заявки, документы, решения и история выбираются с фильтром `owner_id`; чужая заявка возвращает 404.
- Upload ограничен 1 МБ, MIME PDF/PNG/JPEG, файлы хранятся в volume, в БД — метаданные и SHA-256.

## Локальная модель и RAG

Помощник берёт условия из текущего каталога в базе данных: ищет подходящие предложения, передаёт модели их карточки с ID и версией, затем возвращает ответ и массив `sources`. Это RAG поверх структурированных данных; отдельный индекс, векторная БД и модель эмбеддингов для шести предложений не нужны. Если указан `application_id`, backend сначала проверяет владельца заявки. Модель не меняет заявки, не считает платежи и не принимает кредитные решения.

Чат передаёт текущую страницу, выбранные для сравнения продукты и параметры потребности. Backend добавляет профиль авторизованной компании, её заявки, статусы и метаданные документов; для открытой заявки — проверки, решение и историю. Содержимое загруженных файлов в LLM не передаётся. Ответ API содержит `alternatives` с плюсами, условиями и отметкой применимости; frontend показывает их отдельными карточками.

Помощник передаёт локальной модели сведения о текущей странице, выбранных продуктах, компании, заявке, документах, проверках и недавнем диалоге. Модель объясняет недостающие документы, возможные причины отказа, следующий шаг и различия между кредитами. При сравнении двух выбранных кредитов ответ модели проверяется по условиям каталога; если ответ неполный или противоречивый, возвращается проверенное сравнение с `mode: verified-comparison`. Дополнительные варианты показываются только тогда, когда они подходят по цели, сумме, сроку, возрасту бизнеса и выручке.

Рекомендуемая лёгкая модель — `qwen3:4b-instruct` (Q4, около 2,5 ГБ на диске). Если она медленна, можно использовать `qwen3:1.7b` (около 1,4 ГБ), изменив `AI_MODEL`. Скорость зависит от процессора, памяти и выбранного движка; измерьте её на демонстрационном компьютере. Без доступной модели `/api/assistant` возвращает `mode: deterministic-fallback`, а основной кредитный сценарий не прерывается.

### Разработка через LM Studio

1. Загрузите Qwen3 4B Instruct в квантованном GGUF-варианте, откройте вкладку Developer и запустите локальный API-сервер. На машине разработки уже проверен вариант `qwen3-4b-instruct-2507` от Unsloth в Q4_K_M.
2. Локальный backend по умолчанию обращается к `http://127.0.0.1:1234/v1` и модели `qwen3-4b-instruct-2507`. Если идентификатор загруженной модели отличается, укажите **точный ID** в `backend/.env` или переменной `AI_MODEL`. После изменения `.env` перезапустите backend.
3. Docker backend по умолчанию обращается к `http://host.docker.internal:1234/v1`; запустите сервер LM Studio с доступом с хоста Docker. Если идентификатор модели другой, замените `AI_MODEL` в корневом `.env`. Локальный сервер не должен быть доступен из Интернета.

На Apple Silicon LM Studio поддерживает движки `llama.cpp` и MLX; для небольшой плотной 4B-модели это практичнее, чем движки, рассчитанные на крупные MoE и высокую параллельную нагрузку. Выбор между GGUF/llama.cpp и MLX следует делать по замеру на конкретном ноутбуке.

Backend использует OpenAI-совместимый `/v1/chat/completions`. По умолчанию разрешены локальные адреса `localhost`, `127.0.0.1`, `host.docker.internal` и Compose-сервис `ollama`; внешний HTTPS endpoint требует явного включения. Проверить запрос можно через `docs/api-examples.http` после входа под демо-аккаунтом: **`mode: local-llm` подтверждает реальный вызов настроенной модели**, `deterministic-fallback` означает ответ без неё. Чат показывает этот режим и названия найденных карточек.

Модель можно запускать **отдельно от Docker**; PostgreSQL, bank-mock, backend и frontend запускаются в Docker. Эксперт может подставить собственные `AI_BASE_URL`, `AI_MODEL` и `AI_API_KEY` через корневой `.env`. Внешний HTTPS endpoint разрешается только при `AI_ALLOW_REMOTE=true`; основной сценарий от него не зависит. В этом случае `mode: local-llm` означает успешный вызов настроенной модели, включая удалённую. Подробный порядок, объём передаваемых данных и отдельные проверки — в [документе об ИИ и справочнике](docs/ai-and-catalog.md). Распознавания содержания банковской выписки в текущем MVP нет: проверяется наличие загруженного синтетического документа.

### Резервный запуск модели в Docker

Ollama включён в Compose как необязательный профиль `ai`; обычный `docker compose up --build` не загружает модель. Для автономной проверки:

```bash
docker compose --profile ai up -d ollama
docker compose --profile ai exec ollama ollama pull qwen3:4b-instruct
AI_BASE_URL=http://ollama:11434/v1 AI_MODEL=qwen3:4b-instruct docker compose --profile ai up -d --build
```

Модель хранится в volume `ollama_data`. На macOS Docker-контейнер с Ollama обычно не использует Metal-ускорение хоста; для разработки и быстрой демонстрации на Mac предпочтительнее LM Studio вне Docker. Стек Docker остаётся работоспособным без профиля `ai`.

Полная интерактивная спецификация — `/docs`; внутренний endpoint bank-mock не включён в публичную спецификацию backend и защищён отдельным ключом между сервисами.

## Жизненный цикл заявки

`DRAFT → SUBMITTED → CHECKING → SCORING → DECISION_PENDING → APPROVED/REJECTED → OFFER_ACCEPTED → SIGNED_DEMO → DISBURSED_DEMO`; при нехватке документов или по запросу сотрудника переход в `NEEDS_INFO` и повторная отправка. Решение фиксирует сотрудник банка через отдельный кабинет. Все переходы валидируются backend-ом и пишутся в историю. Результаты предыдущих попыток проверок сохраняются.

```bash

```

Тесты используют временную SQLite-базу и временную папку загрузок, поэтому не меняют локальные демо-данные.

Старый browser-local симулятор можно отдельно проверить через `npm run test:legacy`. Полный чек-лист для самостоятельной сквозной проверки находится в [тестовых сценариях](docs/test-scenarios.md). Проверки интерфейса не выполняются командой `npm test`.

## Ограничения демо

- Данные компаний, ФНС, БКИ и финансовых источников — тестовые.
- Скоринг и ограничения одобрения — прозрачные демонстрационные правила, не банковская модель и не финансовая рекомендация; окончательное деморешение фиксирует сотрудник.
- `DISBURSED_DEMO` означает только завершение демонстрационного сценария; реальные деньги не переводятся.
- Ответ модели основан на найденных карточках каталога, но генеративный текст следует проверять; API отклоняет ставки, отсутствующие в найденных карточках, и использует резервный ответ при ошибке модели.
- Используемые компоненты и смоделированные интеграции перечислены в `THIRD_PARTY_NOTICES`.
